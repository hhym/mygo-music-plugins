# 探测基线（2026-11-23 修订）

这是修完一轮问题之后的全量结果，和当天上午那版（可播 15）不是同一份数据。两次之间改了三件事，后面「变化」一节写清楚。

方法：每个插件独立进程加载 → `home()` 取第一首（首页只有专辑时顺着第一个专辑取一首）→ `stream()` 拿地址 → 对地址发一个 1 KB 的 `Range` 请求，看状态码与 MIME。单插件上限 90 秒。

判读：`206/200` 算可播；`403/503` 是出口被站点拒绝，不一定是插件问题；`stream 报错` 要看报什么，兜底源失败和逻辑错误要分开。

## 和上午那版为什么差这么多

上午的 15 可播不是站点都坏了，一半是我自己的探测脚本有问题：

1. **探测脚本截断 id**：`probe-one` 把 track 的 id 前 24 个字符拿去展示，又用这个截断值去调 `stream()`。凡是 id 是 URL、uuid、`netease:…` 这种长串的插件（GD音乐台、米乐迪、无名音乐、优折美、听书类）全部误报「没有可用地址」。已修。
2. **蜻蜓 FM 兜底集体失效**：飞行读书、单田芳评书网、听FM电台、悦听吧、275听书这五个插件共用同一段兜底代码，取音频原来抓 `m.qtfm.cn/vchannels/<chid>/programs/<pid>/` 页面里的 `audioUrl`。2026-11 起那个页面变成 SPA 空壳，页面里没有 audioUrl，于是兜底 100% 返回 null。改成 `webapi.qtfm.cn/api/mobile/channels/<chid>/programs/<pid>` 取 `programInfo.audioUrl`，再解出它的 302 `location`（带 `auth_key` 的签名 m4a）。实测 `qtfm:432367:1` 与 `qtfm-prog:432367:20339917` 都回 206。
3. **超时上限从 45 秒放宽到 90 秒**：米粒音乐、单田芳这类首页串行抓多页的站，45 秒不够，会被误标「崩溃」。

所以 15 → 24 里有 5 个是兜底修好的，4 个是探测脚本自己误报的。

## 怎么用

```bash
node scripts/probe.mjs              # 全量，出表
node scripts/probe.mjs 36dj-music   # 只探一个
node scripts/probe.mjs --json       # 机器可读，gate.mjs 用的就是它
node scripts/gate.mjs               # 和 docs/基线.json 比，有退化就退出 1
```

基线文件是 `probe.mjs --json` 的原始输出（`docs/基线.json`），带时间戳，`gate.mjs --update` 收新基线。
